# API-контракт — «Учебный планер»

Версия контракта: `1.0`. Базовый путь: `/api`. Запросы и ответы используют JSON; даты — `YYYY-MM-DD`, время — ISO 8601 в UTC. SQLAlchemy-схема учебной базы и seed-данные находятся в `app/models.py` и `project.db`; CRUD пользователей пока остаётся целевой спецификацией.

> **Статус реализации:** endpoints `/tasks` реализованы в текущем приложении, но таблица задач пока не содержит `user_id`. CRUD `/users` и связь с пользователем — целевая спецификация, ещё не реализованная. Перед включением пользовательских endpoints нужно добавить миграцию/инициализацию обеих таблиц и привязку задач к пользователю. Аутентификация и авторизация в этой учебной версии не входят в контракт; не публикуйте endpoints пользователей в открытый интернет без защиты.

## Общие правила

- Успешное создание возвращает `201 Created` и созданный объект.
- Успешное чтение и изменение возвращает `200 OK`.
- Успешное удаление возвращает `204 No Content` без тела ответа.
- Некорректный запрос — `422 Unprocessable Entity`; объект не найден — `404 Not Found`.
- Email пользователя уникален; повтор email возвращает `409 Conflict`.
- Поля `id`, `created_at` и `updated_at` назначает сервер. `updated_at` меняется при каждом успешном изменении.
- Удаление пользователя каскадно удаляет его задачи.

## User — пользователь

| Метод | Endpoint | Назначение | Успех |
| --- | --- | --- | --- |
| `POST` | `/api/users` | Создать пользователя | `201`, объект User |
| `GET` | `/api/users` | Список пользователей | `200`, массив User |
| `GET` | `/api/users/{user_id}` | Получить пользователя | `200`, объект User |
| `PATCH` | `/api/users/{user_id}` | Изменить переданные поля | `200`, объект User |
| `DELETE` | `/api/users/{user_id}` | Удалить пользователя и его задачи | `204` |

Создание (`POST /api/users`):

```json
{
  "name": "Аня",
  "email": "anya@example.com"
}
```

Для `PATCH` допускается передать непустое подмножество `name` и `email`. `name` — строка длиной 1–100 символов после удаления крайних пробелов; `email` — валидный email длиной не более 254 символов.

Ответ User:

```json
{
  "id": 1,
  "name": "Аня",
  "email": "anya@example.com",
  "created_at": "2026-10-31T12:00:00Z",
  "updated_at": "2026-10-31T12:00:00Z"
}
```

## Task — учебная задача

| Метод | Endpoint | Назначение | Успех |
| --- | --- | --- | --- |
| `POST` | `/api/tasks` | Создать задачу пользователя | `201`, объект Task |
| `GET` | `/api/tasks` | Список задач | `200`, массив Task |
| `GET` | `/api/tasks/{task_id}` | Получить задачу | `200`, объект Task |
| `PATCH` | `/api/tasks/{task_id}` | Изменить переданные поля | `200`, объект Task |
| `DELETE` | `/api/tasks/{task_id}` | Удалить задачу | `204` |

`GET /api/tasks` принимает необязательные query-параметры `user_id` и `status`; допустимые статусы: `planned`, `in_progress`, `done`.

Создание (`POST /api/tasks`):

```json
{
  "user_id": 1,
  "title": "Подготовить доклад",
  "description": "Найти источники и сделать слайды",
  "due_date": "2026-11-10",
  "status": "planned"
}
```

`user_id` должен ссылаться на существующего пользователя. `title` обязателен, после удаления крайних пробелов имеет длину 1–200 символов. `description` — строка до 2000 символов, по умолчанию пустая. `due_date` — необязательная дата или `null`. `status` по умолчанию `planned`. Для `PATCH` разрешено передать непустое подмножество `user_id`, `title`, `description`, `due_date`, `status`; `null` разрешён только для `due_date`.

Ответ Task:

```json
{
  "id": 42,
  "user_id": 1,
  "title": "Подготовить доклад",
  "description": "Найти источники и сделать слайды",
  "due_date": "2026-11-10",
  "status": "planned",
  "created_at": "2026-10-31T12:00:00Z",
  "updated_at": "2026-10-31T12:00:00Z"
}
```

## Форма ошибки

```json
{
  "detail": "Задача не найдена."
}
```

## Соответствие приложению

Сейчас реализованы `POST /api/tasks`, `GET /api/tasks`, `GET /api/tasks/{task_id}`, `PATCH /api/tasks/{task_id}` и `DELETE /api/tasks/{task_id}`. Фактический список поддерживает `status`; параметр `user_id` и поле `user_id` в Task появятся после реализации целевой схемы.
